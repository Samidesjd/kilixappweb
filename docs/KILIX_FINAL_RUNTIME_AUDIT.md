# Kilix — Final Runtime / Database Contract Audit

## النتيجة
تم توحيد عقد قاعدة البيانات على migration واحدة رئيسية: `supabase/migrations/000_canonical_schema.sql`، بينما migrations من 001 إلى 004 أصبحت توافقية فارغة حتى لا تُنشئ عقدًا موازيًا.

## التدفقات التي تم تدقيقها

### الحسابات
- التسجيل ينشئ مستخدم Auth ثم ينشئ/يكمل سجل `public.users` تلقائيًا.
- لكل حساب `user_code` فريد بصيغة `KX-XXXXXXXXXX` ويُحفظ في قاعدة البيانات.
- تسجيل الدخول يعيد تحميل الملف الشخصي والمتجر المرتبط من `auth_id`.
- لا توجد شاشة تعتمد معرفًا ثانيًا للمستخدم كهوية قاعدة بيانات.

### المتجر
- إنشاء المتجر يستخدم `owner_id = auth.uid()`.
- `store_code` يُولد من قاعدة البيانات وليس من الشاشة.
- المتجر مرتبط بحساب واحد `owner_id UNIQUE`.
- إنشاء/تعديل المنتجات لا يتم قبل وجود متجر.

### المنتجات
عقد المنتج الموحد:
`title`, `price`, `description`, `category`, `template`, `sizes`, `colors`, `ram`, `storage`, `images`, `videos`, `is_active`.

الفئات: `electronics`, `clothing`, `home`, `construction`.

القوالب: `clothing`, `computer`, `phone`, `watch`, `home`.

- الاسم 1–150 حرفًا.
- الوصف إلزامي وبحد أقصى 1000 حرف.
- السعر موجب.
- صورة واحدة على الأقل.
- الصور: jpg/jpeg/png/webp حتى 10MB.
- الفيديو: mp4/mov/avi/webm حتى 100MB.
- تعديل المنتج يرسل فقط الحقول التي تغيرت ولا يعيد إدخال قيم افتراضية فوق الحقول غير المعدلة.
- توليد embedding للصورة أصبح مسارًا فعليًا عبر Edge Function بعد حفظ المنتج، بدون تعطيل حفظ المنتج عند غياب إعداد Hugging Face.

### الطلبات
التدفق الموحد:
`pending → shipping → delivered → completed`
مع الحالات النهائية `out_of_stock` و`cancelled`.

- السعر النهائي يأتي من `products.price` داخل RPC، وليس من السعر القادم من الواجهة.
- بيانات العميل، الولاية، البلدية، نوع التوصيل والملاحظة تُحفظ في `orders`.
- الطلب يصل للتاجر عبر استعلام المتجر وRealtime.
- تأكيد التاجر يستخدم RPC محمي بملكية المتجر.
- نفاد المخزون يستخدم نفس مسار RPC.
- تأكيد الاستلام يستخدم RPC من حساب المشتري فقط.
- بعد التأكيد تظهر شاشة التقييم.

### السلة
بعد نجاح إنشاء الطلب يتم وضع نفس المنتج والكميات والخيارات في السلة المحلية، مع بقاء الطلب المصدر في `orders`.

### التقييمات
- لا يمكن تقييم طلب قبل وصوله إلى `delivered`.
- إنشاء التقييم يتم ذريًا عبر `create_order_review`.
- التقييم ينقل الطلب إلى `completed` ويضع `reviewed=true`.
- متوسط التقييم والعدد والتوزيع يُعاد حسابها في Trigger قاعدة البيانات.
- خدمة عرض تقييمات المنتج تعمل بحد افتراضي 4 تعليقات، وشاشة المنتج تستخدم هذا الحد في جلب التعليقات.

### المتجر والمتابعون
- عدد المتابعين مصدره `store_followers` ويتم تحديث `stores.followers_count` عبر Trigger.
- منتجات StoreDetail تأتي من `products` الحقيقية.
- صورة البطاقة مأخوذة من `products.images[0]`.
- متابعة/إلغاء المتابعة عبر RPC.
- مراسلة صاحب المتجر تنشئ/تستعيد محادثة حقيقية.

### المحادثات
- كل محادثة مرتبطة بمعرفي Auth حقيقيين.
- الرسائل في `chat_messages`.
- إنشاء المحادثة عبر RPC.
- ChatScreen لم يعد يتعامل مباشرة مع Supabase؛ كل العمليات تمر من `chatService`.
- رسالة تأكيد التاجر تُنشأ من Trigger قاعدة البيانات بعد نجاح تحديث الحالة، لمنع الرسائل المكررة.
- قراءة الرسائل وRealtime موحدان.
- حذف المحادثة ينفذ حذفًا حقيقيًا بدل مجرد الرجوع للشاشة.
- مشاركة المحادثة تستخدم مشاركة النظام بدل رسالة "قريبًا".

### الإشعارات
- إنشاء الإشعارات من Triggers / خدمة قاعدة البيانات.
- دعم الطلب، الشحن، نفاد المخزون، الرسائل، التقييم، المتابعة، والدفع.
- Orders وNotifications لديهما تحديث لحظي.

### الفوترة
- `gross_order_value * 0.001`.
- يبدأ طلب الدفع عند وصول الرصيد المستحق إلى `500 دج`.
- سجلات الدفع مرتبطة بالمتجر وصاحبه، والتسجيل لا يسمح بدفع يتجاوز الرصيد المستحق.

### Storage
- Buckets: `media`, `avatars`.
- مسار media مرتبط بمتجر صاحبه؛ لم يعد أي مستخدم موثّق يستطيع الكتابة عشوائيًا داخل مسار متجر آخر.
- avatars مرتبطة بمستخدم Auth.
